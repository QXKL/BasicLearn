# 第 001 节: AOP 是什么

## 这一节的目标

学完这一节，你只需要能回答一句话:

`AOP 是把很多方法里都会重复出现的公共逻辑，单独抽出来统一处理。`

## 先别急着背概念

先想一个业务方法:

```java
createOrder("Java 入门书")
```

这个方法最核心的任务，其实只有一个:

`完成下单`

但真实项目里，我们往往还会顺手加上这些代码:

- 打印请求参数
- 记录执行时间
- 判断当前用户有没有权限
- 记录异常信息

这就会带来一个问题:

`业务代码` 和 `公共辅助代码` 混在一起了。

方法一开始还很简单，后面会越来越胖，越来越难看。

## AOP 想解决什么问题

AOP 的思路很直接:

不要把日志、权限、异常处理都塞进业务方法里。

把这些“很多地方都要重复写”的逻辑抽出来，在方法执行前后统一加上去。

这就像给方法外面包了一层“增强功能”。

业务方法继续专注做业务，公共逻辑交给切面处理。

## 用你现在项目里的代码来看

在 [aop_quick_start_000](/E:/JavaProjects/BasicDemo/basicDemo/src/main/java/com/qx/basicdemo/AOP/aop_quick_start_000) 里，可以这样理解:

- `OrderService`：真正做业务的人
- `LogAspect`：专门负责“额外加日志和异常记录”的人
- `AopDemoRunner`：把示例跑起来的人

也就是说:

`OrderService` 不需要自己关心“前后打印什么日志”。

这些增强动作可以由 `LogAspect` 统一接管。

## 为什么它叫“面向切面”

因为它处理的不是某一个单独方法的核心流程，
而是“横着切进很多方法里的公共逻辑”。

比如日志:

- 下单方法要打日志
- 取消订单方法要打日志
- 查询订单方法也要打日志

日志这件事，不属于某一个业务方法独有，
它是“横切”在很多方法上的。

所以 AOP 很适合处理这类逻辑。

## 这一节你先记住这两个判断

如果一段代码:

- 在很多方法里都会重复出现
- 它又不是业务本身的核心目标

那么它通常就很适合考虑用 AOP。

## 一个最朴素的对比

不用 AOP:

- `createOrder()` 里写业务
- 还要自己写日志
- 还要自己记异常
- 还要自己记耗时

用了 AOP:

- `createOrder()` 只管业务
- 日志、异常、耗时由切面统一处理

## 这一节先别混淆的一点

AOP 不是用来替代 OOP 的。

它是对 OOP 的补充。

OOP 负责把业务对象组织清楚。

AOP 负责把“公共增强逻辑”从业务代码里拆出来。

## 小结

这一节只要吃透一句话就够了:

`AOP = 不改原业务代码，也能在方法前后加统一的公共功能。`
